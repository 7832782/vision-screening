## 0. 三条贯穿全项目的原则

| 原则 | 具体表现 |
|---|---|
| **老人能独立完成 > 功能多** | v0.6 删掉了所有演示性质的模态；一屏只让用户做一个决定；按钮最小 64 px 高、主按钮 92 px |
| **宁可测低，不可测高** | 算法自检显示系统性偏保守（真值 0.0 测成 0.1）；筛查宁可多转诊，不能漏诊 |
| **每一个数字都要能解释** | 屏幕上限不许报成真实视力，一律 `≥X · 受屏幕限制`；结果页给出三种记法和分级依据 |

第三条是踩过坑才写下来的：用户全做对却被告知视力 0.2，那个 0.2 其实是屏幕上限。

## 一、校准：为什么必须拿实物量

### 系统 API 拿不到可信的物理尺寸

Android 各家 `xdpi` 常年报错，浏览器只给 CSS 像素和 `devicePixelRatio`，**没有任何 API 能告诉你
1 CSS px 等于多少毫米**。WHOeyes 的取巧办法是假设「屏幕对角线恒为 5 英寸」——
这在 6.7 英寸手机上会错 25%，等于整个测量的尺度是错的。

**唯一可靠的办法：拿一个已知尺寸的实物去量。**

### 实现（`index.html` 的校准页）

- 内置参照物按组放在一个下拉框里（共 7 项），默认身份证短边 54 mm：
  - 卡片：身份证 / 银行卡 短边 **54.0 mm**、长边 **85.6 mm**
  - 纸张：A6 105、A5 148、A4 210
  - 其他：1 元硬币 **Ø25 mm**、**自定义长度**
  - 纸张长度按「短边」用：A4 长边 297 mm 比手机屏还宽，v0.9.6 已删
- **自定义长度**：输入任意已知毫米数（尺子、书、桌边都可以），程序按该长度算 PPI
- 三种调节方式是同一份状态的三个入口：**拖动两端手柄** / **拖滑条** / **± 大按钮**（照顾不会拖动的老人）
- 未校准时的起步猜测：`DEFAULT_MM_PER_CSS = 0.19`（≈134 ppi），**只影响标尺初始长度**，拖一下就对
  （原来还有个「输入屏幕英寸数算 PPI」的兜底，v0.9.6 删掉了，理由见第九节）
- 结果存 `localStorage['vs.calib'] = { mmPerCssPx, method, at }`，下次不用再校准；
  换算入口是 `devPerMm() = devicePixelRatio / mmPerCssPx`

### 两个必须点出来的坑

**① 身份证长边 85.6 mm 比绝大多数手机屏幕还宽。**
以 6.1 英寸手机（约 65 mm 物理宽度）为例，长边根本放不进屏幕 —— 所以手机端默认用**短边 54 mm**，
长边和纸类留给平板和一体机。

**② 实物会挡住标尺。**
做法：手柄画在屏幕最上方（`top:6px`），用 2 px **亮黄 `#ffd23f`** 竖线延伸下来指向端点，物品放在下方 ——
手指压住物品也挡不到手柄。标尺条本身用纯白底，亮黄手柄在暖白页面上一眼就能找到。

### 误差分析（决定要不要做精细校准）

| 参照物 | 屏幕上的长度 | 1 CSS px 对应 | ±1 px 相对误差 |
|---|---|---|---|
| 身份证短边 54 mm | ≈ 260 px | 0.208 mm | 0.38% |
| 1 元硬币 25 mm | ≈ 120 px | 0.208 mm | 0.83% |
| A4 长边 297 mm | ≈ 1200 px | 0.248 mm | 0.08% |

结论：**只要物品长度 ≥ 50 mm、对齐误差 ≤ 2 px，视标尺寸误差 < 1%**，
远小于视力测量本身 0.1 logMAR 的量化精度，够用。

### 还没解决：浏览器整页缩放

Chrome 的 `Ctrl +/-`、部分国产浏览器的「页面缩放」会让 CSS 像素与物理毫米的换算整体失效。
计划用 `visualViewport.scale !== 1` 或 `devicePixelRatio` 与记录值不符时提示重新校准 —— **尚未实现**。

## 二、距离：为什么「动态」要拆成三种

### 线性部分严格成立

视标在视网膜上的大小由**视角**决定：

```
θ ≈ 2·arctan(h / 2d) ≈ h / d   （小角度）
```

logMAR 定义在视角上，所以 **h ∝ d 严格成立**：距离翻倍 → 尺寸翻倍 → 结果不变。
在 h/d < 0.05 rad（≈2.9°）范围内 `tan` 与线性近似的偏差 < 0.1%，可以放心。

### 但有三个硬约束，让「任意距离」两头都走不通

**① 屏幕分辨率下限（近端限制）**
距离越近，同一档 logMAR 需要画的物理尺寸越小。E 的笔画只有高度的 1/5：

| 距离 | logMAR 0.0 的 E 高度 | 400 ppi 手机 | 102 ppi 21.5″ 一体机 |
|---|---|---|---|
| 2 m | 2.91 mm | 45.8 px ✅ | 11.7 px ✅ |
| 1 m | 1.45 mm | 22.9 px ✅ | 5.9 px ✅ |
| 0.4 m | 0.58 mm | 9.2 px ✅ (笔画 1.83 px) | 2.3 px ❌ (笔画 0.47 px) |

**② 调节需求（远端限制，对老年人尤其致命）**
2 m 处只需 0.5 D 调节，老花眼基本无感；1 m 处需要 1 D。
没戴老花镜的老人会**把 1 m 的远视力测低** —— 这不是等价变换。

**③ 近视力不能改距离**
「近视力」的定义里包含晶状体在 40 cm 的调节状态。改成 60 cm 测的就是另一件事（老视程度变了）。
**近距必须固定在一个标称距离。**

### 所以我们这么做

- **远距**：2 米（默认）/ 1.5 米 / 1 米 / 自定义 1–5 米；切到 1 米会明确提示「老年人可能低估」
- **近距**：33 / 40 / 45 cm 三档，默认 40（标准）；**在「近距离测试说明」页选**，选完再点开始，
  和远距「先选距离再开始」是同一套流程（v0.9.3 从设置页挪过来，因为设置页离操作太远）
- 视标尺寸随距离自动换算（`optotypeHeightMm(logMAR, distM)`），可测上限随距离自动重算

> **把「动态」拆成三种，别混为一谈**
>
> 1. **距离可配**（已实现）：人量好距离填进去，程序按 `h ∝ d` 换算 —— 最稳的「动态」。
> 2. **实时测距**（可做，未做）：前置摄像头 + 人脸关键点，用**瞳距**（成人平均 63 mm）反推距离。
>    2 m 处 720p 画面里瞳距约 40 px，±1 px → ±2.5% 距离误差 → ±0.011 logMAR，完全可接受；
>    但暗光、侧脸、老花镜反光会让检测失败，必须留「检测不到就退回手动输入」的降级路径。
>    另一个坑：距离抖动会让视标尺寸「呼吸」，必须加滞回（变化 >5% 才重算）。
> 3. **真·任意距离不量**：不行。不测距就不知道视角，等于把 logMAR 的定义扔了。

### 距离怎么量（现实问题）

- 最稳：卷尺 / 2 米地面胶带
- 次稳：打印一条 2 米纸带（A4 拼 7 张，模板未做）
- 凑合：成人步长 ≈ 0.7 m，2 米约 3 步（误差 5–10%，不推荐）
- 近距 40 cm：A4 长边 29.7 cm + 手掌宽 8–10 cm，或直接「一臂再加一拳」

## 三、可测上限：最容易被误解的一个数字

### 上限怎么算

`maxRenderableIndex(distM)` 从**最高档往下找第一个「笔画 ≥ 1 个设备像素」的档位**，找到就返回。
规则只有这一条，因此结果**随距离单调**：距离变远，同一档的视标变大，只会更容易画出来。

### 为什么不能拿「像素吸附误差 ≤10%」当上限判据

早期版本用「笔画 ≥ 1 px **且** 吸附误差 ≤ 10%」筛上限，结果出现：

| 距离 | 上报的最高档 |
|---|---|
| 33 cm | 小数 0.50 |
| 40 cm | 小数 **0.20** |
| 45 cm | 小数 0.63 |

33 cm 能测 0.5、40 cm 只到 0.2、45 cm 又能测 0.63 —— 完全不符合物理直觉。
根因是整数像素吸附（`k = round(devPx/5)`）在不同距离下「碰巧对齐得好 / 不好」，
把上限判据交给吸附误差，就等于把物理规律交给了运气。修法是**把两件事拆开**：

- **上限**只判「画不画得出来」→ 笔画 ≥ 1 设备像素（单调）
- **绘制**才考虑吸附：误差 ≤ 10% 就吸附到整数像素，否则按精确物理尺寸绘制

这样上限单调，绘制也不牺牲精度。修复见 `docs/版本史.md` v0.9.1。

### 不同屏幕的上限（按现在的规则算）

| 设备 | 33 cm | 40 cm | 45 cm | 1 m | 2 m |
|---|---|---|---|---|---|
| 手机 6.1″ 1080p 400 ppi | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |
| 平板 10.9″ 264 ppi | 0.80 | 1.00 | 1.00 | 1.00 | 1.00 |
| 一体机 21.5″ 4K 205 ppi | 0.63 | 0.80 | 1.00 | 1.00 | 1.00 |
| 一体机 21.5″ 1080p 102 ppi | 0.32 | **0.40** | 0.50 | 1.00 | 1.00 |
| 一体机 24″ 1080p 92 ppi | 0.32 | 0.40 | 0.40 | 1.00 | 1.00 |

（数字由 `tools/cap_table.py` 按 `index.html` 同一套公式算出，可重跑核对。）

**两个结论**：
1. **远距 2 米几乎所有设备都能测到 1.0** —— 远距不是瓶颈，近距才是。
2. **近距对低 PPI 大屏是死路**：1080p 21.5″ 在 40 cm 最高只到 0.40，刚好卡在「视力下降」判定门槛附近，
   等于分不出正常与轻微下降。近距请用手机 / 平板（约 400 ppi）或 4K 屏。

所以界面上到顶时显示「**≥0.20 · 受屏幕限制**」并解释：不是你的视力只有 0.20，是这块屏幕画不出来。

## 四、像素吸附与绘制：既要精确又要看得清

tumbling E 的笔画宽度 = 高度的 1/5。只有高度是 5 的整数倍设备像素时，每一笔才落在整数像素上，
不会被抗锯齿糊掉 —— 这是 WHOeyes 比一般视力 App 精细的地方，我们照搬了它的一半：

```js
k = Math.round(devRaw / 5);              // devRaw = 视标高度（设备像素）
if (Math.abs(5*k - devRaw) / devRaw <= 0.10) size = 5*k / dpr;   // 吸附
else size = devRaw / dpr;                                        // 精确绘制
```

**只吸一半的原因**：无条件吸附等于偷偷改了视标尺寸（最大 ±10%），而视力对尺寸是敏感的；
反过来说，误差 ≤10% 时视标高度仍在同一档位内，吸附换来的是边缘干净、没有灰边。

### 视标太大放不下时怎么办

2 米外 logMAR 1.0 的 E 高约 58 mm，加上拥挤框会超出手机屏幕。WHOeyes 的做法是 `overflow:hidden`
直接把框裁掉。我们改成**优先保 E 的真实尺寸**，按顺序压缩拥挤框的参数：

```
avail = min(屏宽, 屏高) × 0.94
extra = avail - size                    // 还剩多少空间给框
drawFrame = min(frame, extra × 0.25)    // 先压框线（原本 = 笔画宽）
gap       = max(0, (extra - 2×drawFrame) / 2)   // 再压间距（原本 = 高度的一半）
只有当 size 本身 > avail 时，才缩小 E
```

顺序不能反：**缩小 E 会让视力被高估**（视标变小 → 更容易看错 → 结果偏低，但这个「偏低」是假的）。
压框只是牺牲一点拥挤效应，不影响视标本身。

## 五、阶梯法

每组 **5 个视标，答对 4 个通过**；通过后 **+2 档（0.2 logMAR）**；首次失败记下档位 F，回退 1 档做确认：

| 情况 | 结果 |
|---|---|
| F-1 通过 | F-1 |
| F-1 失败 | F-2（最后一次通过的档位） |
| 连最大视标（logMAR 1.0）都失败 | `< 0.1` |
| 一路通过到屏幕上限 | 该档 + `受屏幕限制` |

比 WHOeyes 少一次「回退 3 档」的冗余轮次（它退到 F-3，但 F-2 一定是已通过的档，所以 F-3 这轮不影响结论），
题量更少、结论等价。逐行推导见 [WHOeyes-逆向分析.md](WHOeyes-逆向分析.md) §3 §4。

## 六、作答方式：从「堆模态」到「做减法」再到「只接离线模块」

| 阶段 | 做法 | 结果 |
|---|---|---|
| 阶段一（v0.1–v0.5） | 按键 / 滑动 / Web Speech / 自研 MFCC+DTW 语音 / Python 后端（SenseVoice + MediaPipe） | 模态齐全，但要开机、要联网、要维护四套链路，老人用不上 |
| 阶段二（v0.6） | **做减法**：删掉所有语音 / 手势，只留按键 + 滑动 | 代码减半，把精力还给校准和距离这两个真正影响准确度的环节 |
| 阶段三（v0.8 起） | 重新整合**纯前端、纯离线**的两个模块：Vosk WASM 语音 + MediaPipe Hand 手势 | 静态托管就能跑，不需要后端和 CDN；默认关闭，开启才申请权限 |

现在的四种作答：**四个大方向键（上/下/左/右排列）**、**全屏滑动**、**外接键盘方向键**、**语音 / 手势**。
无论哪种方式提交，对应方向按钮都会绿色闪一下 —— 老人需要确认「我说的话真的被听到了」。

### 两个交互细节都是踩坑来的

- **连续作答 1 秒硬缓冲**：语音 / 手势连续作答时，上一题的声音或手势会被带到下一题。
  现在每题作答后显示「下一题准备…」硬等 1 秒，语音引擎和手势闸门同时进入 1 秒冷却。按键 / 滑动不受影响。
- **远距换眼 5 秒倒计时自动继续**：换眼原来要等人点确认，一个人做的时候没人点。
  现在 5 秒自动进另一只眼，也可以点「立即换另一只眼」。

### 手势闸门（`gesture/gesture_gate.js`）

21 点手部关键点 → 食指伸直度 + 方向角，再由闸门决定「这次算不算一次作答」：
动作激活（足够大的位移）→ 保持 **400 ms** 确认 → 置信度门槛 **0.45** → 本题已答则进入冷却
（闸门默认 800 ms，`gesture/engine.js` 按 1 秒硬缓冲的要求覆盖成 **1000 ms**）→ 手离开画面后可重新武装。
静止垂手、讲话时的自然挥动都不会误触发。只认 **1 只手**（`numHands: 1`）—— 老人单手作答，多识别一只手只是白耗算力。

### 预览框：为什么用 `contain` 而不是 `cover`

摄像头流和预览框的比例经常不一致。手机竖屏时 `getUserMedia` 常给 **480×640 的竖幅流**，
而预览框是 **4:3 横幅**：

| 方案 | 480×640 流放进 358×269 的框 |
|---|---|
| `cover` | 放大 0.747 → 480×478，**上下各裁掉 105 px**。举起的手在画面顶部，直接被裁到框外 |
| `contain` | 缩小 0.42 → 202×269，左右各留 78 px 黑边，**画面完整** |

一个必须看见「手举起来没有」的工具，宁可留黑边也不能裁掉手 —— 裁掉之后骨架点会落到画布负坐标，
用户看到的是「手在画面里、点不在手上」，怎么修映射公式都没用（v0.9.3–v0.9.4 就是这样连续修错两轮）。

配套两条：
- 预览框的 `aspect-ratio` **跟随 `video.videoWidth/videoHeight`**，比例一致时不会出现黑边
- 骨架按 `Math.min(vrw/vw, vrh/vh)` 缩放 + 居中偏移，和 `contain` 完全一致

### 手机当遥控器（推荐但未做）

一体机场景的真实矛盾：

> 屏幕要正对 2 米外的老人，操作的人（助手）要么看不到屏幕所以不知道老人指哪，
> 要么看得到屏幕就等于看见了答案（WHOeyes 论文里专门讲要 mask the examiner）。

解法：**一体机显示二维码 → 家属手机扫码 → 手机上出现四个超大方向键 → 点一下，局域网回传给一体机**。
零额外硬件、手机会话只走局域网、天然解决「助手是否看到答案」。见 [路线图.md](路线图.md)。

## 七、适老化交互决策

| 决策 | 依据 |
|---|---|
| 基准字号 `clamp(17px, 1.05vw + 13px, 25px)`，随屏幕放大 | 老年人阅读舒适字高 ≈ 18–20 px |
| 普通按钮最小高 64 px，主按钮 92 px，作答按钮 82 px | 手指点击热区 ≥ 44 px，老人手抖要留余量 |
| 方向按钮字 `1.9em`，首页卡片最小高 150 px | 视觉上「一眼就知道按哪」 |
| 暖白底 `#f7f4ed` + 墨黑字 + 墨绿主色 `#0d6b5c` | 纯白刺眼、纯黑沉重；对比度远超 WCAG AA |
| `user-scalable=no` + `overscroll-behavior:none` | 老人误触双指缩放会毁掉屏幕校准，必须禁 |
| 一屏只给一个决定 | 首页只有「远距测试 / 近距测试 / 校准 / 历史」四张大卡 |
| 横屏（一体机）让卡片撑满中间区域并居中 | 1366×768 上两张 150 px 卡片挤在顶部、中间一大片空白，看着像没做完；横屏改成两列 + `min-height:40vh` + 内容居中，手机竖屏不动 |
| 语音播报告诉你「现在测右眼，请遮住左眼」 | 一个人也能做，不需要助手念 |
| 界面**不写**自我说明与自我背书 | v0.9.7 删掉了设置页页脚那段「算法参考 WHOeyes（WHO / CERA「Vision at Home」）…数据不离开本机」——用户读完不需要它也能正常使用，属于元陈述。判断标准：删掉之后用户会不会少信息或做错事？不会就不该有 |

## 八、架构决策：为什么坚持单文件、无构建、无 CDN

```
index.html（主页面，含 CSS + 内联脚本）+ voice/（Vosk WASM）+ gesture/（MediaPipe WASM）
```

- **一体机往往是老旧的 Android WebView**：任何 CDN 依赖都可能加载失败，`type="module"` 都可能不支持
- **断网可用**：语音 / 手势的 WASM 和模型全部放在项目本地，首次加载后走浏览器缓存
- **交付成本为零**：老师 / 评委打开网址就能用，不需要 npm、不需要装 App、不需要后端
- 代价：`index.html` 到 v0.9.4 已经 1900 行；这是**刻意接受的**，因为改动通常在
  「引擎层 / 交互层」两处，分区注释足够定位（分区表见 [架构与代码.md](架构与代码.md)）

## 九、被否掉的方案

| 方案 | 为什么否掉 |
|---|---|
| 假设屏幕对角线 5 英寸（WHOeyes 的做法） | 6.7 英寸手机上错 25%，等于整个测量的尺度错了 |
| 让用户输入手机型号查 PPI 表 | 型号库无穷无尽，且同一型号可能有不同屏 |
| 无条件把视标吸附到 5 的整数倍 | 等于偷偷改视标尺寸最大 ±10% |
| 用「吸附误差 ≤10%」筛可测上限 | 会让上限随距离非单调（33 cm 比 40 cm 还高） |
| 视标放不下时等比缩小视标 | 缩小 E 会让视力被高估 |
| 用 Web Speech API 做语音识别 | 依赖云端、要联网、中文识别对老人方言不友好 |
| 自研 MFCC + DTW 模板匹配 | 要自学习模板，换个说话人就不准 |
| 云端 / 本地 Python 后端做识别的**默认**路径 | 静态托管场景没有后端；只在「高精度模式」里作为可选（未接入） |
| 语音播报时暂停识别（防自听） | 会阻塞识别；用户要求先观察设备是否真的自听（v0.9.3 暂时移除） |
| 让用户输入屏幕英寸数来估算 PPI | 桌面屏上会错 3–4 倍（CSS 像素对角线 ≠ 物理尺寸），而且是「猜」不是「量」；v0.9.6 连同入口一起删 |
| PWA（manifest + Service Worker） | 只服务「装到桌面、断网打开」，本程序扫码即用，做完还要维护缓存版本；v0.9.6 删除 |
| 手机当遥控器（二维码 + 局域网方向键） | 想法好但要加后端，破了「纯静态」底线；v0.9.6 从路线图删除 |
| 摄像头实时测距（瞳距反推） | 暗光 / 侧脸 / 老花镜反光都会失败，还得留手动降级；不如把距离量准 |
| 服务端高精度语音（24/24） | 需要一台电脑常开，静态站点没有后端；浏览器版 83.3% 已够筛查 |
| 把 `index.html` 拆成多个文件 | 无构建前提下拆文件会引入加载顺序问题，收益只是好看 |
