# 4 方向「食指指向」手势识别：方案调研 + 原型实测

> 任务：识别 4 种手势——食指指上 / 下 / 左 / 右；越轻量越准确越好。
> 结论日期：2026-11-07（Asia/Shanghai）
> 实验目录：`F:\DeepSeek Harness\项目\vision-screening\_gesture_lab\`
> 说明：项目主线 v0.6（另一个 AI 维护）已删除语音/手势模态；本目录是「重做手势模态」的实验，未改任何项目源码（`git status` 干净）。

## 0. 一句话结论

**有现成底座，没有现成 4 方向模型。** 最佳方案是
**MediaPipe Hand Landmarker（21 个手部关键点，7.46 MiB，Apache-2.0）+ 自研 4 类判定 + 时间稳定 + 动作激活闸门**：

- 识别：手部关键点上做规则判定即可，**dataset 上 29/29 次给出方向时全部正确**（precision 100%），代价是水平（手/构图太差时返回 none）——排除 40 cm 纯手部特写后准确率 **85%**；
- 轻量：模型 7.46 MiB；本机 Python CPU 单帧 **20–26 ms**；浏览器 WASM（GPU）**11 ms** / CPU 41 ms；完全离线；
- 没有直接输出 up/down/left/right 的公开模型：MediaPipe Gesture Recognizer 内置 8 类里只有 `Pointing_Up`，其余 3 个方向必须自研；
- 最大风险不是「4 分类」，而是**静止垂手被误判为「向下指」**（15 张负样本里 6 张误报）。必须加「动作激活 + 每题一次」闸门（已实现并单测通过），并在真实老人身上验证。

## 2. 方案对比（为什么是 Hand Landmarker + 自研 4 类）

完整调研（含每个数字的来源与证据分级）见 [`research-web.md`](research-web.md)。摘要：

| 方案 | 形态 / 体积 | 能否直接给 4 方向 | 实测/证据 | 结论 |
|---|---|---|---|---|
| **MediaPipe Hand Landmarker** | 21 点，7.46 MiB（palm 2.23 + landmark 5.23） | 否，需自研 4 类 | 本机 Python 20–26 ms；官方 Pixel 6 CPU 17.1 ms / GPU 12.3 ms；本机浏览器 GPU 11.3 / CPU 41 ms | **首选**（Python 或浏览器都行） |
| MediaPipe Gesture Recognizer | 7.99 MiB（内含同一 HandLandmarker） | 内置只有 `Pointing_Up` | 官方 8 类清单 | 只能当「是否在指」闸门，4 方向仍需自研 |
| MediaPipe Model Maker | 自定义手势训练 | — | 官方已弃用；只支持 Python 3.8–3.10 / TF<2.16 | 排除（本机 Python 3.12 也装不上） |
| TFJS handpose + fingerpose | 权重约 12 MB + tfjs 运行时 | 可自研 | 官方弃用、浏览器 CPU 性能差 | 备选，不推荐 |
| RTMPose / mmpose hand | 检测器 + 2.58 GFLOPs 关键点模型 | 可自研 | 精度更高但重，部署复杂 | 精度优先时才考虑 |
| YOLO11n-pose 手部社区权重 | 约 6 MB | 可自研 | 无官方权重、数据/许可（AGPL）风险 | 不推荐 |
| OpenVINO hand pose | 只是推理运行时 | 需自备手部模型 | 无现成手部模型 | 不适用 |
| OpenCV 肤色 + 凸包/凹陷 | 极轻（几 KB 代码） | 可写启发式 | 光照/肤色/背景敏感，误判高 | 仅演示/兜底 |

**关键旁证**：Google 自己的 `gesture_recognizer.task` 里，手势分类头只有 **7,773 字节**（输入是 21×3 关键点，不碰像素）；也就是说「在关键点上做 4 分类」本身极轻，重的是关键点检测底座。

## 3. 推荐方案与算法细节

### 3.1 模型与调用

- 模型：`hand_landmarker.task`（float16，7,819,105 B = 7.46 MiB，Apache-2.0），内含 palm detector + 21 点回归。
- 运行：`num_hands=2`（两只手中挑「最像指向」的那只，避免漏判），`RunningMode.VIDEO`（跟踪上一帧 ROI，只有丢失时才重跑 palm 检测，实测比每帧全图检测省 30% 且更稳）。
- 输入：摄像头帧 JPEG（640×480 即可；2 m 场景建议 ≥480p，详见 §4.4）。

### 3.2 纯几何判定（`hand_engine.classify_hand_landmarks` / `hand_rules.js`）

1. **手掌尺度** `hand_px = |腕(0) − 中指MCP(9)|`；用 `hand_px / min(画面宽,高)` 做分辨率无关的尺度门限（避免同一只手换分辨率判定漂移）。
2. **食指伸直度** = `|TIP(8)−MCP(5)| / 指节折线长`；要求 ≥0.60，且比中指/无名指/小指中**最直的那根**至少再直 0.04（排除张开手掌、握拳、竖拇指）。
3. **食指 2D 长度** `|TIP−MCP| / hand_px ≥ 0.25`：食指朝镜头戳时 2D 投影会塌缩，这种方向不可信，直接判 none。
4. **方向角**：`atan2(-(y8−y5), x8−x5)`，按 45°/135° 分四象限；并要求 `max(|dx|,|dy|)/|v| ≥ 0.78`（斜向死区，避免 45° 附近来回跳）。
5. **置信度** = 0.40×伸直度 + 0.25×食指优势 + 0.25×主方向占比 + 0.10×尺度。
6. **时间稳定**：窗口 6 帧、连续 4 帧同向才切换（10–15 fps 下约 0.25–0.4 s），单帧抖动不改变结果。
7. **镜像语义**：前端自拍预览 `scaleX(-1)` 时用 `mirror=True`（判定前把 x 翻成 `1−x`，即「受试者视角」）；或先把帧镜像、再 `mirror=False`，两者等价。返回的 landmarks 永远是未镜像原始坐标。

### 3.3 作答闸门（解决静止垂手误报，`gesture_gate.AnswerGate`）

单帧规则不能区分「手自然垂在体侧、食指朝下」和「故意向下指」——实测 15 张负样本 6 张误报。因此加一层状态机：

- **动作激活**：手腕在 0.5 s 窗口内移动 ≥ 画面尺寸 2% 才「开始作答」；静止手不触发。
- **保持确认**：激活后方向稳定保持 400 ms 才发一次作答事件。
- **每题一次 + 中性重置**：一次作答后必须等「手消失 ≥0.6 s」或「方向持续 none ≥0.8 s」才允许下一次；每题开始时调用 `reset_question()`，并要求先回中性再指。
- 单测 7/7 通过（静止手 90 帧 0 误报、抬手后只答一次、持续举着不重复、离开可重新武装、1% 抖动不触发、低置信度不触发、有动作无方向不触发）。

> 这层是**产品正确性的关键**，不是可选项：老人坐在 2 m 外手放腿上时，单帧规则会持续输出「向下」。

## 4. 实测数据（本机：R5 5600 / 32 GB DDR4-3600 / 无 GPU 参与推理）

### 4.1 数据集与准确率

数据集 `dataset/`：**55 张**（AI 生成 38 + AI 镜像 8 + 公开真实照片 9），`labels.csv` 逐张标注；构图分 far（≈2 m 全身）、upper（≈1 m 半身）、close_selfie（≈40 cm 胸上自拍）、close（40 cm 纯手部大特写）；负样本 15。详见 [`dataset/README.md`](dataset/README.md)。

IMAGE 模式（`mirror=False`，逐图）结果：

| 子集 | 数量 | 检出 | 方向正确 | 命中率(含未检出) | 检出后准确率 |
|---|---:|---:|---:|---:|---:|
| far | 11 | 9 | 9 | 82% | 100% |
| upper | 16 | 15 | 14 | 88% | 93% |
| close_selfie | 7 | 6 | 6 | 86% | 100% |
| **排除 close 大特写（实用子集）** | **34** | **30** | **29** | **85%** | **97%** |
| close（40 cm 纯手特写，产品不会出现） | 6 | 1 | 0 | 0% | 0% |
| 全部正样本 | 40 | 31 | 29 | 72.5% | 94% |
| 真实公开照片 | 9 | 6 | 5 | 56% | 83% |
| AI 图（含镜像） | 31 | 25 | 24 | 77% | 96% |

**方向混淆矩阵（全部正样本）**：所有错误都是「未输出（none）」，**没有一次 up/down/left/right 互相判错**。也就是说：在当前数据上，**只要模型给出方向，就是对的（29/29）**；漏判主要来自检测不到手。

漏判/失败案例的具体原因（真实照片）：
- `real_right_03`（消防员，戴手套）未检出——MediaPipe 模型卡明确写手套/遮挡不在适用范围；
- `real_up_02`（棒球运动员远景举手）、`real_right_02`（户外远景老人）手在画面里太小，未检出；
- `real_down_02`（俯身指地上的孩子）检出手但其他手指伸展、方向不明确 → none；
- 40 cm 纯手部大特写（手占满画面、无身体上下文）几乎全部检不出——**产品里不要用这种构图**，用 close_selfie（脸 + 手都在画面）即可（86%）。

负样本误报（15 张，6 张误报 = 40%）：静止垂手 `nohand_01`→down、`hang_01`→down、手扶桌 `table_01`→down、双手叉背 `back_01`→down、端杯 `hold_01`→up、双手同时指 `twopoint_01`→up（最后一张其实是有效「指上」，属标签口径问题）。**这就是 §3.3 闸门存在的理由**；静态数据集无法验证闸门，需要真实视频。

### 4.2 延迟

| 场景 | p50 | p95 | 说明 |
|---|---:|---:|---|
| Python IMAGE，原始图片（939×1408 / 1024²，含 JPEG 解码） | 26.2 ms | 35.3 ms | 55 张逐图 |
| Python VIDEO，640×480 帧 | 20–22 ms | — | 连续帧，含 JPEG 解码 |
| Python VIDEO，320×480 帧 | 19–21 ms | — | 下限分辨率 |
| 浏览器 tasks-vision 0.10.21，640×480，GPU delegate | **11.3 ms** | 13.2 ms | tracker 锁定时（ego-lite / Chromium 156） |
| 浏览器同场景，CPU delegate | 40.7 ms | 43.5 ms | 最坏 65 ms |
| 官方 Pixel 6（HandLandmarker 整条 pipeline） | CPU 17.1 ms / GPU 12.3 ms | — | 官方 benchmark |

作答延迟 ≈ 每次指方向需要：动作激活（抬手）+ 4 帧稳定（0.25–0.4 s）+ 闸门保持 400 ms ≈ **0.7–1 s**，老人答题节奏可以接受；实际应用建议每题留 1.5–2 s。

### 4.3 2 m 小目标验证（关键）

把 far 构图照片缩到不同宽度，模拟「固定分辨率摄像头 + 2 m 外的手」，**每个分辨率都用全新引擎冷启动**（不靠上一个分辨率的 tracker 预热），连续送 12 帧：

| 帧宽（竖图） | 手部尺度 | 4 方向结果 |
|---|---:|---|
| 640 | 33–49 px | **8/8 全对** |
| 480 | 25–37 px | **8/8 全对** |
| 320 | 17–25 px | 6/8（左、镜像右漏判） |

结论：**640×480 是可用下限，480×640 也稳；320×240 不够。** 若摄像头能到 1280×720 更稳（手 ~40–50 px）。VIDEO 模式的跟踪会先检出再锁 ROI，比单帧模式在小目标上更稳。

### 4.4 浏览器端（无 Python 后端的路线）

详见 [`browser/REPORT.md`](browser/REPORT.md)（含原始 JSON）。要点：

- **可行**：ego-lite（Chromium 156）里 CPU/GPU delegate 都能跑，完全离线（把 jsDelivr/googleapis 全 block 后 0 外部请求）。`file://` 双击打开不行（CORS 拒绝），必须 HTTP(S) 静态服务。
- **体积**：wasm 9.13 MiB + 模型 7.46 MiB + JS ≈ **16.9 MiB**（本地不压缩首屏）；走 brotli 的 CDN/静态服务器约 **10.1 MiB**。
- **版本选择**：`@mediapipe/tasks-vision@0.10.21` 优于 `1.2.2`（wasm 9.57 vs 14.60 MiB、CPU 快 8–12%、且 1.2.2 会向 `odml.pa.googleapis.com` 发遥测）。
- **注意**：每创建一个 `HandLandmarker` 实例都会重新拉 wasm + 模型，产品必须全局只建 1 个实例；建议 GPU 优先、CPU 回落、检测节流 10–15 fps。

### 4.5 真人快速验证（非严格）

用本机 A4tech 640×480 摄像头 + `live_demo.py` 做「随机方向提示 → 用户指 → 记录对错」的 8 题演练。第一轮因提示文字未渲染（已修）无效；第二轮（提示可见）结果 **4/8**：左、右、下、上各有一次正确识别（conf 0.99–1.00，左右镜像语义正确），错误为 1 次「上一题残留姿势被当成本题答案」、3 次「手一直举着导致闸门未重新武装而超时」。第三轮用户离开摄像头，未产生有效数据。

结论：**方向判定在真人手上可复现**；需要修的是答题节奏与闸门状态（每题先回中性、题间留 1.5–2 s、超时提示），以及**真实老人试用**（本报告尚未覆盖）。

## 6. 集成建议（二选一，按部署形态）

### A. 浏览器端（适配 v0.6 单文件、无后端）——推荐

- 资源：`@mediapipe/tasks-vision@0.10.21`（本地 vendoring js+wasm，约 9.6 MB）+ `hand_landmarker.task`（7.46 MB）+ `hand_rules.js`（约 5 KB）+ `gesture_gate`（约 5 KB）。
- 接入：设置里开「手势作答」→ 点击后首次加载模型（16.9 MB，可缓存）→ `getUserMedia` 取 640×480 → 每 80–100 ms 送一帧 `detectForVideo` → 稳定方向 + 闸门 → 触发与滑屏/方向键相同的作答函数。
- 要求：HTTPS（手机摄像头）、只建 1 个 HandLandmarker 实例、GPU delegate 优先 / CPU 回落、8–15 fps 节流、页面不可见时暂停。
- 风险：老 Android WebView 的 wasm 性能未知（需真机测）；首屏多 16.9 MB；GitHub Pages 可用（静态 HTTP）。
- 演示页：`browser/index.html`（静态图片自测）、`browser/live.html`（摄像头实时）。

### B. Python 后端（沿用 v0.5 架构，有电脑/一体机旁有 PC 时）

- `hand_engine.py` 直接替换 v0.5 的 `pose_engine.py`：接口形状一致（`detect(jpg_bytes) -> dict`，含 `gesture/confidence/landmarks/debug`），WebSocket 只需把「direction」事件换来源。
- 延迟 20–26 ms/帧，CPU 占用低；无需改前端摄像头采集方式。
- 依赖：mediapipe 1.2.2（或 0.10.x），模型 7.46 MB；模型路径中文问题沿用 `_ascii_safe_model_path`。
- 缺点：现场必须有一台电脑跑后端（v0.6 已把这套去掉，属于重新引入）。

**选择建议**：若目标是「手机/一体机独立可用、不摆电脑」，走 A；若团队更看重稳定与已有 v0.5 的 WebSocket 通道、现场能放电脑，走 B。两条路的算法与判定代码相同（`hand_engine.py` / `hand_rules.js` 已对齐，浏览器实测 6/6 一致）。

## 7. 独立复核与已修复问题

独立复核报告：[`verify/REPORT.md`](verify/REPORT.md)（复核员用 MediaPipe 原生 API 重写判定，46 张上与主引擎逐图预测 46/46 完全相同）。发现并已修复：

1. **`MIN_AXIS_RATIO=0.70` 是死代码**（该比值数学下界 0.7071）→ 改为 0.78，斜向死区真正生效（修正后数据集中无方向互判错）。
2. **NaN/Inf 关键点**会输出 `down` + NaN 置信度 → 加 `np.isfinite` 检查，直接 none。
3. **手部尺度用绝对像素**（换分辨率判定会变）→ 改为 `hand_px / min(宽,高)` 的比例。
4. **食指朝镜头无下限** → 加 `finger_span ≥ 0.25`。
5. **numHands=1 会漏掉指向的手**（`ai_down_far` 复现）→ 默认 2 只手 + best-of-hands。
6. 浏览器报告里 `ai_down_far` 差异归因、CDN 体积口径等已加更正说明（`browser/REPORT.md` 顶部）。

复核中仍属「口径/未验证」的：浏览器报告的部分重复轮次数字没有原始样本 JSON、无法重算；负样本误报在静态图上是 40%，闸门仅逻辑单测，**尚未在真实视频上量化误报率**。
