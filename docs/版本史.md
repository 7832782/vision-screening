### v0.9.5（14:20）手势预览不再裁切

用户反馈「骨架还是歪的」。加上版本号后重新排查，发现真正的根因不在坐标映射：

手机竖屏时 `getUserMedia` 拿到的是 **480×640 的竖幅流**，而预览框是 `.camera-stage` 的 **4:3 横幅**。
`object-fit: cover` 为了填满框，会把画面按 0.747 放大到 480×478 再**上下各裁掉约 105 px**。
举起的手在画面顶部，正好落在被裁掉的区域里——骨架点被算到了画布负坐标（`y ≈ -29 ~ -72`），
所以屏幕上什么都看不到。用户看到的是"手在画面里、点不在手上"，自然判断成"歪"。

| 提交 | 内容 |
|---|---|
| — | `object-fit: cover` → `contain`（`.camera-stage` 和 `#gesturePip` 都改） |
| — | `draw()` 的缩放从 `Math.max` 改 `Math.min`，与 contain 一致 |
| — | 预览框 `aspect-ratio` 跟随 `video.videoWidth/videoHeight`，比例一致时没有黑边 |
| — | 版本号升到 `v0.9.5 · 手势预览不裁切 v3`，import 查询串升到 `?v=20261108-gesture-fit3` |

**验证**：注入 480×640 假摄像头 → 预览框自动变成 358.4×438.9（=3:4），`videoRect == canvasRect`，
21 个骨架点全部落在手上，食指方向线沿着食指、方向判定「上 / 0.94」。

> 教训：连续两轮都在修"映射公式"，而问题在"内容被裁掉了"。**先确认目标在画面里，再算坐标。**

## 阶段四　2026-11-14 · v0.10.0 按老师反馈重构老人路径

老师看过演示图后的意见是「现在的前端对老年人来说过于复杂」。判断依据是画面本身：
首次使用从打开到看见第一个 E 要过 5 屏、之后要过 3 屏；首页两张卡片各 4 行字；
说明页一屏 300 多字再加一个距离选择器；校准页是下拉 + 数字输入 + 拖两个手柄 + 滑杆 + 加减键。

改法是**把复杂度从老人身上挪到布置设备的人身上**，准确度相关的东西一个没删：

| 改动 | 之前 | 现在 |
|---|---|---|
| 首屏 | 欢迎页 → 首页选项目 → 说明页 | 一屏：标题 + 一行引导 + 「开始」，右上角半透明齿轮 |
| 远近选择 | 首页两张卡片 | 远距固定 2 米；近距只从齿轮里的设置页进 |
| 距离调节 | 说明页 3 个按钮 + 自由输入 | 删除（`settings.distanceM` 仍在） |
| 说明 | 一屏 6 条要点 + 2 段解释 | 压进 3 秒倒计时和语音：「站到 2 米外，请遮住左眼」 |
| 校准 | 7 种参照物下拉、自定义长度、拖两个手柄、滑杆、加减键 | 两条竖线 + 「窄一点 / 宽一点」+「卡好了」，只剩身份证 54mm 和硬币 25mm |

### 三个决定背后的取舍

1. **不给「看不清」按钮。** 有了这个出口老人就不猜了，每档都点，结果系统性偏低；算法本来就把错答当成该档失败。
2. **硬币只写老版 25mm。** 2019 年版第五套 1 元硬币直径改成 22.25mm，差 11%，正好卡在「误差 ≤10% 才吸附」的边缘。
   界面写明「2019 年后的新版硬币更小，不要用」。
3. **不做 APK。** `DisplayMetrics.xdpi` 官方措辞就是 may not be exactly accurate，平板和一体机常填假值，
   只能预填不能免校准；包壳还要引入构建，破坏「无构建」红线。

### 竖放校准的几何

54mm 在 360px 宽的手机上要占 79% 屏宽，两个手柄贴着边框；改成竖放后只占屏高 44%。
两条竖线卡住身份证**竖着放时的宽度**，线间距就是 54mm。

滑杆换成「窄一点 / 宽一点」并在按住时连续变化（1.5% / 60ms），原因是竖排 `input[type=range]`
要靠 `writing-mode` 或已废弃的 `-webkit-appearance: slider-vertical`，老 WebView 都不保证支持。
从 0.19 的猜测值调到真值最坏差 30%，按住 1 秒就够。

### 已知代价（写在这里，防止下次有人当成 bug 去修）

- **语音作答自带约 0.2 logMAR 的偏低误差**：模型实测真人 20/24 = 83.3%，阶梯法要 5 题对 4 题，
  17% 的错识率让本来能过的档位约 20% 概率被判失败。默认全开是用户的明确选择。
- 摄像头常驻小窗：老人可能以为自己被拍。代码只在内存里处理，不录不传。
- 方向键保持原尺寸（没有缩成半透明），远距测试时和 E 抢注意力——为了保住「家属在旁边能按」。
- 权限全部被拒时是死局，程序只能用 toast 提示「请家人帮忙按方向键」。
- 2 米距离靠老人自己估，程序无法校验，只在倒计时和语音里各说一次。

### v0.10.3 三步引导（2026-11-14 晚）

用户：「现在的程序缺一个引导，你看看参考程序的引导是怎么样的，取它好的地方」。

查 WHOeyes 公开资料（[中山眼科中心期刊文章](https://journal.gzzoc.org.cn/article/4588)、
[WHO 官方页](https://www.who.int/teams/noncommunicable-diseases/sensory-functions-disability-and-rehabilitation/whoeyes)、
[Play 商店页](https://play.google.com/store/apps/details?id=org.who.whoeyes&hl=zh)）得到四条事实：

- 教程是**分步**的，不是一屏说明书；内容点名：设备与眼睛齐平、屏幕调到最亮、戴平时戴的眼镜、看 E 滑动作答
- 教程可以回看
- 近距在 iOS 上用前置摄像头自动测距：先伸到臂长，再慢慢拉近，到 40 cm 响一声，然后直接进测试
- 远距会逐步说明，并明确告知「需要另一个人帮忙」

取了前两条，其余没照搬：

| WHOeyes 的做法 | 我们 | 理由 |
|---|---|---|
| 分步教程 | 三步引导（脚本分区 11.5） | 老人一屏只读得进一句话；v0.10 删掉的那屏 300 字说明正是反面教材 |
| 教程可回看 | 齿轮 →「怎么测」 | |
| 摄像头自动测距 | 不做 | 网页端 `getUserMedia` 没有深度，靠人脸像素反推误差 30% 以上，等于给假精度 |
| 「远距需要他人协助」 | 不写 | 语音 / 手势 / 按键都能单人完成，写上等于自降能力 |
| 右眼→左眼→复测右眼 | 不复测 | 多三分之一时间，老人疲劳，收益不明 |

三屏文案：①把屏幕调到最亮 / 平时戴眼镜，就戴着测 ②站到 2 米外，遮住左眼（近距：把手机拿到 40 厘米处，两只眼都睁开）
③看清 E 朝哪边，看不清也请猜一个 / 说方向 · 用食指指 · 按下面的箭头。

实现：`vs.firstRun` 标记，首次点「看远处 / 看近处」进引导；第 3 屏「开始」后继续原流程（校准 → 测试）；
`?sim=` 跳过引导（自动测试用）；回看模式最后一屏是「知道了」，结束后回设置页。
